# Архитектура веб-интерфейса

Документ описывает решения фронтенда: из чего он собран, как обращается к данным, как
показывает оценку и отсутствие данных, как формирует отчёты и что ограничивает решение.
Контракт с бэкендом вынесен в [`api-contract.md`](./api-contract.md).

## Стек и обоснование

| Решение | Почему так |
| --- | --- |
| React 18 + TypeScript | типы контракта описаны один раз и проверяются компилятором на всех экранах |
| Vite | сборка за секунду, результат — статика, которую раздаёт nginx без Node на стенде |
| React Router | маршруты совпадают со ссылками, которыми делятся: `/repo/owner/name` открывается напрямую |
| TanStack Query | кеш, устаревание, повтор запросов и поллинг статуса анализа без собственного стора |
| Собственные SVG-компоненты | кольцо Score, радар и полоски — 4 небольших файла вместо графической библиотеки: меньше вес бандла и полный контроль над состоянием «нет данных» |
| CSS с переменными | светлая и тёмная темы, печатная палитра переопределяется в одном месте |

Глобального стора нет: серверные данные живёт в React Query, состояние фильтров — в
URL, пользовательские мелочи (тема, история запусков) — в `localStorage` с обработкой
недоступного хранилища.

## Слой данных

```
компоненты → хуки (src/api/hooks.ts) → фасад (src/api/index.ts) ─┬→ HTTP-клиент (client.ts)
                                                                 └→ мок-транспорт (mock.ts)
```

Фасад выбирает транспорт по `VITE_DATA_SOURCE`. Компоненты про источник не знают,
поэтому переключение демо-режима на боевой бэкенд не требует правок в UI.

HTTP-клиент добавляет `Authorization: Bearer`, разбирает тело ошибки и превращает её в
`ApiError` с понятным пользователю текстом для кодов 0, 401, 403, 404, 429.

Мок-транспорт читает снимок из `public/mock`, фильтрует и сортирует рейтинг на клиенте,
а запуск анализа проигрывает по стадиям с задержками — включая стадию AppSec, которая
честно помечается как пропущенная из-за отсутствия прав.

## Как показывается оценка

Итоговый Score виден сразу в трёх местах и всегда вместе с полнотой данных:

1. **Кольцо** с числом, буквенной оценкой и подписью «посчитан по N% веса методики».
2. **Таблица «Как получилась оценка»** — категория, её балл, номинальный вес и вклад в
   итог. Сумма вкладов равна Score, поэтому расчёт проверяется на странице глазами.
3. **Радар** по шести категориям. Категории без данных не рисуются нулём: точка
   становится пунктирной, подпись — «н/д», а контур фигуры — штриховым.

Каждая категория раскрывается в список метрик с исходными значениями и источником
(Git-клон, API платформы, AppSec) — путь «оценка → подтверждающий факт» занимает один клик.

## Отсутствие данных

Ключевое требование ТЗ и главный источник ошибок интерфейса, поэтому статус выделен
отдельным типом `DataStatus` и обрабатывается на всех экранах:

| Статус | Что видит пользователь |
| --- | --- |
| `ok` | обычная оценка |
| `partial` | оценка + бейдж «данных по категории N%» и причина |
| `no_data` | пунктирная карточка «Нет данных», причина, «вес 20% → 0% (исключена)» |
| `not_applicable` | «Не применимо» с пояснением, почему оценивать нечего |

Дополнительно на странице анализа есть блок «Полнота данных»: список пробелов,
использованные источники и раскрывающийся список технических ошибок сбора с кодами.
В рейтинге полнота данных — отдельная колонка и фильтр (по умолчанию показываются
репозитории с покрытием не ниже 50%, иначе проект с одной заполненной категорией
соседствует в топе с проверенным по всем шести).

## Пользовательские сценарии

**Публичный**: рейтинг → фильтры по языку, полноте данных, наличию CI → страница анализа
→ факты и рекомендации → выгрузка отчёта. Состояние фильтров в URL, ссылку можно
отправить коллеге.

**Личный кабинет**: `Войти через Я ID` → `/auth/callback` сохраняет токен → `/dashboard`
показывает доступные репозитории → «Анализировать» ставит задачу и открывает экран
прогресса со стадиями сбора → готовый отчёт с рекомендациями и выгрузкой. Повторный
запуск с той же страницы показывает разницу со Score прошлого прогона.

Приватные маршруты закрыты компонентом `RequireAuth`: неавторизованного пользователя он
отправляет на `/login?next=...` и возвращает обратно после входа.

## Отчёты

Markdown собирается на клиенте из объекта отчёта и содержит всё, что требует ТЗ к
странице анализа: ссылку на репозиторий, Score, таблицу категорий с весами и статусами,
раскрытие формулы, сильные и слабые стороны, рекомендации с фактами и ожидаемым
эффектом, раздел об отсутствии данных, ошибки сбора, источники и дату анализа.

PDF — печать страницы. Печатные стили возвращают светлую палитру (иначе тёмная тема даёт
светлый текст на белом листе), убирают навигацию и дописывают адреса ссылок. Проверено:
страница анализа даёт 7 страниц A4 с векторным текстом.

## Доступность и адаптивность

Семантические элементы (`table`, `button`, `nav`, `dl`), `aria-expanded` у раскрывающихся
карточек, `role="progressbar"` у прогресса анализа, видимый фокус, контрастные цвета в
обеих темах. Цвет не единственный носитель смысла: рядом с цветными полосками всегда
есть число или подпись. Раскладка рассчитана на настольные разрешения и не ломается до
640 px.

## Производительность и масштабирование

- Рейтинг запрашивает страницами по 25 записей: рост числа репозиториев не влияет на
  клиент, пагинация и фильтры выполняются на стороне API.
- `placeholderData: keepPreviousData` — при смене фильтра таблица не мигает.
- Статус анализа опрашивается раз в секунду только пока задача в работе.
- Сборка — статика (≈90 КБ gzip), раздаётся с CDN или nginx, горизонтальное
  масштабирование сводится к числу реплик nginx.
- Тяжёлые отчёты не хранятся в памяти: страница анализа работает с одним отчётом за раз.

## Ограничения

- Демо-режим показывает снимок данных на 20–21 сентября 2026 года и Score, посчитанный
  демонстрационной формулой из `tools/build_mock_data.py`; боевые значения приходят из
  витрины сервиса.
- История Score в демо-режиме содержит одну точку: динамика появляется после первого
  планового пересчёта на бэкенде.
- PDF формируется печатью браузера. Вид зависит от браузера пользователя; если нужен
  одинаковый файл для всех, его должен отдавать бэкенд (эндпоинт в контракте описан).
- Бейдж для README требует серверного эндпоинта `/badge/{owner}/{name}.svg`: кнопка
  копирует готовый Markdown, но сам SVG отдаёт бэкенд.
- Путь к проекту содержит кириллицу, поэтому алиасы Vite резолвятся через
  `fileURLToPath`; при переносе в другую директорию это уже учтено.

## Реализованные функции со звёздочкой

| Направление | Что сделано на фронте |
| --- | --- |
| Рейтинг и сравнение | сравнение до четырёх репозиториев, фильтры по языку, наличию CI, статусу Security и полноте данных, поддержка `rank_delta` для динамики позиции |
| Углублённая аналитика | bus factor и распределение авторства, зависшие MR и issues, время до первого ответа — выведены как метрики с подсказками |
| Публичность результата | кнопка копирования Markdown-бейджа для README, публичные ссылки на отчёты |
| AI-возможности | не используются: сводка на странице собирается по фактам отчёта без обращения к модели |
